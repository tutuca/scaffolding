# Architecture

## Code principles

- Modular. A model owns one table - except a **proxy**, which is a second reading of one (`Payment`, `Expense` and `Untriaged` over `Movement`). One class per file, unless trivial: the trivial ones are a table instead, generated by `serializers.base.plain` and `service.base.crud`. A class earns a module by carrying a rule worth reading.
- **No module-level `_` names.** No `_ALLCAPS` "private constants", no `def _helper()` at module level: a module already scopes its names, and the prefix claims a privacy Python does not enforce. Rename for meaning.
- A **domain** is anything involving more than one model where the relation is not trivial (`User -> UserType` is trivial; billing is not). Trivial relations stay in flat CRUD; domains get `service/domain/<name>/`.
- **Imperative shell, functional core.** Model mutators, service functions and viewsets are the shell: they touch the ORM and the adapters. The core is pure functions and dataclasses (`calc.py`, `schemas.py`). See **Where logic lives** below.
- Functions are pure in principle and return `None`, one thing, or a list - never called for their side effects. Side effects live at the shell, explicitly.
- Prefer functions + dataclasses; light OOP where it buys encapsulation and readability (class-based views always, no function-based views).
- Typing everywhere, as a readability aid - not strict formal verification. Enforced in `pyproject.toml`: ruff `ANN` plus mypy `disallow_untyped_defs` / `disallow_incomplete_defs` / `warn_return_any`.
- **No `Any` in `src`** (`disallow_any_explicit`). Name the real type; if it is awkward, name an alias next to the code that owns it, like `DecimalColumn` in `data/models/base.py`. Tests may use `Any` and `Mock` - fixtures are dynamic by nature.
- **No purpose suffixes on names.** No `DTO`, `Command`, `Helper`, `Util`, `Info`, `Data`. The dataclass principle stays, the label goes: what the portal hands back is a `PortalAuthorization`, not a `RecordAuthorizationCommand`. The agreed exceptions are framework and error vocabulary: `...Error`, `...ViewSet`, `...Serializer`, `...QuerySet`, `...Manager` (only ever a Django manager), and the ports' agent nouns (`InvoiceAuthorizer`, `RateProvider`).
- **No bare `except:` and no `except Exception:`** (ruff `E722`, `BLE`). Name the failure you are handling.
- Serialization is DRF's job - serializers in / serializers out. No pydantic.
- **Imports go at the top of the module. Always.** Enforced by ruff `E402` and `PLC0415`. An import that seems to need deferring is a layering problem - rework the dependency instead of hiding it inside a function. The one legal way to import for side effect is an explicit `import_module()` call (see `data/apps.py`, which must register admin classes after the app registry loads).
- Test cases build on each other, as do viewsets and serializers (shared bases: `ScaffoldingModelViewSet`, recipes per model). Conventions: `docs/TESTING.md`.

## Module rules

The accretion guard: a feature's first instinct is the nearest existing module,
so the rules name where each kind of code goes and when a module must split.

- **A module holds one question.** A domain module is named for the question it
  answers. `use_cases.py` holds what the shells call; a second question earns a
  sibling module rather than a longer `use_cases.py` - `savings` is the shape
  (`quotes.py`, `reconciliation.py`, `resolvers.py` beside the fixed four). A
  module past ~400 lines, or a `use_cases.py` past ~800, is a review flag that
  a question needs its own module, and the split follows the question, never
  the caller.
- **Steps are marked apart from entry points.** Inside a module that holds
  both, a comment names the entry points - the functions a shell may call, ids
  in and read models out - and everything else is a step (takes a row, or stays
  inside the domain). Where the two kinds sit apart, the `# Entry points`
  heading does it (`balances/use_cases.py`); where they interleave, the list at
  the top of the module does it (`expenses/use_cases.py`). The marker is what
  tells a second shell which signature it may copy.
- **One namespace per kind in the shell.** In `interface/web/`, a view module
  holds views, figures live in `charts.py`, and the `*_rows` formatters a
  template reads live in `rows.py` - a view file that grows formatters is
  accretion wearing a view's name. Money formatting lives once: `pesos` is
  defined in `charts.py`, the CLI's own copy (`balances.py`) is
  the debt this rule retires, and the fix is one module every shell may import
  - not a third copy.

## Where logic lives

Four sources shaped this, and they disagree:

- [Tom Christie, *Django models and encapsulation*](https://www.dabapps.com/insights/django-models-and-encapsulation/): "Never write to a model field or call `save()` directly. Always use model methods and manager methods for state changing operations."
- [James Bennett, *Against service layers in Django*](https://www.b-list.org/weblog/2020/mar/16/no-service/): a service layer is a private second ORM. Put logic in models, managers and querysets.
- [Octopus Energy conventions](https://github.com/octoenergy/public-conventions/blob/master/conventions/django.md): the operational detail - factories/mutators/queries grouping, filters on querysets not managers, properties never hit the database.
- [`tutuca/django_service_layer`](https://github.com/tutuca/django_service_layer/tree/master/src/reservas): the `conf`/`data`/`service`/`interface` layout this project inherits, with a deliberately thin `service/`.

We follow Tom, take the mechanics from Octopus, and keep one narrow service layer that Bennett would delete. The order of preference, strongest first:

**1. Model mutators own every write.** Nothing outside `data/models/` assigns a model field or calls `save()`. A state change is a named method that says what happened in the business - `invoice.authorize(...)`, `invoice.reject(...)`, `invoice.file_document(...)` - and that method is the only place the fields behind it move. This is the rule the rest hangs off; it is enforced by a test (`tests/scaffolding/test_conventions.py`), not by good intentions. One named exception, written in the code that makes it: `data/admin/base.py`'s `save_formset`/`save_model` assign the taxpayer and save inline rows directly, because `formset.save()` goes around the mutators and `same_taxpayer` would never see those rows - the admin is the only place the invariant can be stated.

**2. Factories own creation.** `Invoice.objects.draft(...)` creates the invoice *and* its line, valued and consistent, in one call. No `objects.create()` from outside the model that owns the table.

**3. QuerySet methods own every query worth naming.** On the queryset, never the manager, so they chain: `Invoice.objects.authorized().rolling_year_to(date)`. Declared with `Manager.from_queryset(...)` outside the class body, which is what django-stubs needs.

**4. Service functions own orchestration that spans a model and the outside world** - and nothing else. `service/domain/<name>/use_cases.py` holds plain functions that read fields, call adapters, and hand results to model mutators. This is the deliberate divergence from Bennett: authorizing an invoice means opening a SOAP connection to ARCA, and a model method has no business doing that. The test of whether code belongs here is "does it need a port?" - if not, it belongs on the model.

**5. ViewSets translate HTTP into domain calls and back.** One call into the domain per action; no rules of their own.

**6. A workflow is one domain entry point, and every UI gets it for free.** When
naming a movement means three things - pin the categoría, make sure the taxonomy
can hold it, re-run the pass - those three live behind one function in
`service/domain/`, not in whichever screen happened to need them first. A shell's
only job is to say *which* inputs: the admin reads them off a changelist row, the
CLI off repeated `--name`, a viewset would read them off a payload. Each is a
different way of collecting the same pair; none of them is a different workflow.

A background task is the same shell one more time: `interface/tasks` collects
JSON-serializable inputs off the queue, wires the ports, and calls the entry
point - never re-implements it. Composition follows the same rule: a basic task
(`fetch_ipc`, `load_movements`) is a building block a larger task (`fetch_inflation`)
calls or enqueues, and where the domain already composes the workflow
(`billing.monthly`, `movements.run_pipeline`) the task calls that rather than
re-chaining its steps, so the idempotency the domain owns stays in one place.

The test is the one in the heading: could a second interface be added without
copying anything? `expenses.name` is the shape - the admin's `save_model` is one
line and `movements triage` is a loop over argv. The failure mode it is written
against is real and was written here first: the recategorize pass lived in
`UntriagedAdmin.save_related`, so naming a movement in the admin did one thing
and naming it from the CLI did another, and nothing in the suite could see it.

The same rule decides where a side effect goes. It belongs to the use case that
causes it, not to the caller and not to the model mutator - a mutator that ran a
domain service would make `data/` depend on `service/`, which is the layering
backwards.

**7. An entry point takes ids and returns read models; a step takes rows.** Rule 6
says every UI gets the workflow for free. This is what makes that true rather
than aspirational, because a signature is what a second shell actually collides
with. Four properties, each decidable by reading the source:

- **Keyword-only parameters.** argv binds by position and a JSON payload binds by
  name; `*` is the only thing both can spell.
- **No ORM or filesystem type in the signature**, in or out. A `Model` is
  something each shell would look up differently, a `QuerySet` cannot cross HTTP,
  and a `Path` is something only a CLI has. `load_report` takes the transcript's
  text; `authorize` takes an invoice id.
- **Returns a dataclass or a primitive.** `Comprobante`, not `Invoice` - and it
  carries the id, because the next step in the chain names its subject by id.
- **Refusals are `DomainRefusal`**, which every shell already maps: a
  `CommandError`, a 400, an admin message.

**Which books is an id too.** `taxpayer` is the first argument of almost every
entry point here, and it is the taxpayer's id, not the row - because "which
books" is the one question each shell answers completely differently: the CLI
from `--taxpayer` or the single registered taxpayer, HTTP from the `X-Taxpayer`
header or the profile's active set, the admin from the row being edited. Only the
answer travels, and an id is the only shape all three can produce. `owned_by`
takes the id for the same reason, so an entry point scopes without a lookup.

The two are named apart, everywhere: **`taxpayer` is the id, `books` is the row.**
A shell that needs the row needs it to wire a port - the ARCA certificate, the
Drive folder - and wiring a port is the shell's job, so it fetches one and calls
it `books`. Nothing then reads `taxpayer=books`, which is what the single name
kept producing.

The counterweight is that a domain still needs functions that take a row -
`send_for_cae(invoice)`, `draft_credit(invoice, ...)`, `link(invoice, ref)` - and
those are **steps**, grouped under their own heading in `use_cases.py` and reached
only from inside the domain. An entry point is a thin wrapper over a step: it
looks the row up, calls the step, and maps the result. `billing` is the shape,
because `monthly` chains four steps and no shell should have to know that.

The lookups that belong to the domain, not the shell: `active_contract` and
`punto_venta` lived on `ScaffoldingCommand`, which made "exactly one active contract
in these books" and "these books have a punto de venta" rules the CLI had and a
viewset would have had to rewrite. Neither is a choice a shell makes, so no entry
point takes a punto de venta as an argument any more - `monthly`, `catch_up` and
`crosswalk` read it off the taxpayer they were already given.

Also adopted from Octopus: group model members under `# Factories`, `# Mutators`, `# Queries`, `# Properties` comments; a `@property` never triggers a database query (so `Settlement.effective_rate`, which reads only its own columns, is a property, while `Invoice.get_uncredited_amount()`, which reads through a reverse FK, stays a method); `__str__` identifies one instance; prefer `.get()` over `.first()` when exactly one row is expected, and `order_by` explicitly whenever order matters.

Not adopted, with reasons: **`Meta.ordering` stays.** Octopus bans implicit ordering, but the admin is this tool's primary UI and DRF pagination needs a deterministic order; the cost they are avoiding (surprise ordering on large queries) does not apply to one taxpayer's ledger. **Field names stay Spanish** where they are ARCA's own field names (`fecha_emision`, `punto_venta`) - they are transcribed onto a fiscal form, and translating them would cost more than the `_at`/`_date` suffix convention buys.

**No validation in `save()`, and no `save()` overrides.** This follows from Octopus's warning: `update()`, `bulk_update()` and `bulk_create()` never call `save()`, so a rule enforced there is a rule that can be walked around - while reading as though it cannot. Invariants go in one of three places instead, strongest first:

- **A database constraint**, for anything that must hold however the row is written. `Invoice` `authorized_is_complete`: an AUTHORIZED row cannot lack its CAE, número, vencimiento, rate or peso valuation. `Movement.category` is a foreign key into `CategoryGroup` for the same reason: a categoría nobody has grouped cannot be stored, so the reports cannot be asked to total a name the taxonomy has never heard of. The key is `to_field="category"`, so the column still holds the word a rule emitted and `category_id` still compares as a string - what the constraint adds is that the word has to be a row.
- **A mutator that refuses, or is idempotent**, for transitions, which a constraint cannot see (they compare the old row to the new one). `freeze_valuation()` no-ops once `amount_ars` is set, so no path can revalue an issued comprobante.
- **Prevention in the UI**, for the interactive path. `InvoiceAdmin.get_readonly_fields` locks the frozen fields once authorized.

`Invoice` carried a `save()` override with a frozen-field check until 2026-09-09. It cost a `SELECT` on every write, had to mirror Django's `save` signature exactly, and protected only paths that rule 1 and `InvoiceAdmin` already close - while the doc had to disclaim it in the same breath. The constraint that replaced it is strictly stronger, because `update()` cannot go around it.

## Data, not hierarchy

Encapsulating mutation (above) is about *where writes happen*. It is not a licence to model everything as an object graph. The counterweight is [Bergin and Winder's *Understanding OOP*](http://www.csis.pace.edu/~bergin/patterns/ppoop.html), which answers "print a judgment about the operating system" with an interface, a factory, four singletons and a registry - and Rob Pike's reply, that the right answer is to **search a small table**, and that "sometimes data is just data and functions are just functions".

So:

- **A table beats a hierarchy.** A `dict`, `frozenset` or tuple of rows plus a search is clearer and cheaper to extend than a class per case. The adapter registry (`AUTHORIZERS`), the holiday set (`calendar.HOLIDAYS`), the frozen field list (`FROZEN_AFTER_AUTHORIZATION`) and the monotributo scale are all tables that get searched, deliberately. Adding a case means adding a row.
- **An `if` is not a failure of imagination.** "Every `if` is a lost opportunity for dynamic polymorphism" is the claim this project rejects. Two branches are two branches.
- **Table-driven tests.** When the same assertion applies to many inputs, one `parametrize` over a list beats N copied test bodies - see `test_registration.py` and `test_conventions.py`.
- **Inheritance only where the framework demands it** (`models.Model`, `ModelViewSet`, `Serializer`) or for a genuinely shared field set (`TimeStampedModel`). Reuse between adapters is a shared *function*, not a base class - see `next_number_from_db`.
- **A class earns its place by bundling data with behaviour that varies.** The ARCA adapters qualify: each really does something different. A class whose methods are all `@classmethod`, that exists only to raise `NotImplementedError`, or that only forwards every call to another object, does not - write the function, or write nothing until there is behaviour to write. `WsfexClient` implements both ports for that reason: one service, so a class per port held nothing but a renamed call.

## Principle

The ledger is a **derived read model**. ARCA holds the CAEs; the bank holds the movements. This database must be reconstructible from those two sources plus the contract. Every design choice below follows from that.

## Layers

```
interface/api        HTTP: `urls.py` holds the router and the versioned prefix
                     (`/api/v<major>.<minor>/`), and `service/views.py` the two
                     tables it walks. Knows nothing about the domain beyond those
                     tables.
interface/web        The views, and no templates. `HomeView` takes `/` ahead of
                     the admin - who you are and `access.gaps`; the three book
                     pages (`movimientos`, `inversiones`, `planes`) are each
                     rendered by `interface/web/books.py` from tested reads and
                     `charts.py` figures; `AdminLoginView` shadows `/login/`.
                     Not an installed app: a plain module `conf/urls.py` imports,
                     like `interface/api`.
interface/cli        Management commands - argv in, stdout out. Its own Django app
                     so the CLI can import service/ without the data layer
                     depending on it. `base.py` maps a refusal to a CommandError
                     the way `service/base.py` maps it to a 400; `portal.py` holds
                     the Comprobantes en línea round trip that `month` and
                     `creditnote` both make.
interface/tasks      The fourth shell: the cadence as `django.tasks` `@task`
                     functions over the same use cases, one file per workflow
                     (`market`, `inflation`, `movements`, `month`, `balances`,
                     `archive`, `experiment`). A task collects JSON-serializable
                     inputs, wires its ports, and calls the entry point - no logic
                     and no ORM writes of its own; basic tasks compose into larger
                     ones. A plain module, not an app: tasks are imported by name,
                     never discovered. `TASKS` runs `django-tasks-db`'s database
                     backend: a task enqueues as a row on the `tasks` database
                     (routed by `conf/router.py`) and `scaffolding db_worker` runs it.
                     Dates, decimals and enums cross the wire as strings, converted
                     at the call site with `date.fromisoformat`/`Decimal`.
ui/                  What the tool looks like: one `:root` of tokens, the
                     chrome, and the overrides that dress the admin and allauth.
                     An app, because that is Django's unit for templates and
                     static, and first in INSTALLED_APPS because `APP_DIRS`
                     takes the first match. No views and no models - it is at the
                     project root rather than under `interface/` because it takes
                     no input from outside. It has also grown the Python tools the
                     templates and the charts read - `contract.py` (the model
                     contract a form is generated from), `forms.py`, `pager.py`,
                     `schema.py` and `templatetags/grid.py`.
interface/adapter    Everything external - ARCA, the bank/rail reports (`extractos`),
                     the household bills (`bills`: ecogas, epec and italia, parsed
                     into the `Bill` table), the free rate mirror (`mirror`: EMBI+,
                     MEP and CCL), Google Sheets, INDEC's IPC and BCRA's reference
                     rates. Ports are Protocols; adapters implement them.
                     `AdapterError` at the root; one subpackage per outside system.
service/             ViewSets. `views.py` is two tables - `RESOURCES`, the CRUD
                     surface generated by `base.crud`, and `ACTIONS`, the ones with
                     behaviour of their own. domain/<name>/ for use cases.
data/                The one Django app: models, serializers, admin, migrations.
data/models/         …including `Movement`, the one table money that moved lands in,
                     `Goal` and `Obligation`, which the projection walks forward,
                     `AccountBalance` and `Cutoff`, the asserted stock and the
                     date it is closed through,
                     (`Payment`, `Expense` and `Untriaged` are proxy readings of it),
                     `ReversalEntry`, the valuation journal: what a reversal netted
                     when it was recorded, and `Bill`, one utility bill's rows,
                     written by the `bills` adapter's parsers.
data/serializers/    Five carry a rule on the wire and keep a module; the rest are
                     `base.plain(model)` rows in a table.
bin/                 Operator tools, run by hand, never imported by the app.
```

Dependency direction: `interface/{api,web,cli} → service → data`, and `service → interface/adapter` through Protocols only.

Three documented exceptions, each named where it happens - an exception that is
not written down is drift:

- `interface/adapter/arca/manual.py` imports `data.models`. Its "outside system"
  is our own `ExchangeRate` table - the portal bridge reads a hand-loaded rate,
  and `next_number_from_db` reads our own ledger because ARCA is not being asked.
- `billing/use_cases.py` imports `arca.registry`'s `get_authorizer` and
  `get_rate_provider` - a lookup into the selection table, not a call on an
  adapter, but the registry reaches the ORM through `manual`, which is the very
  import the surface is kept free of. Present since `e4246a8`; the fix is moving
  the selection to the shells, which already choose in every other case. Kept
  here so the break reads as admitted rather than accidental.
- `data/admin/untriaged.py` calls `expenses.payees` - the one workflow call a
  `data/` module makes into `service/`. The admin's save must re-run the
  categoría pass so the screen redraws a ledger that already reflects the
  decision; the alternative splits one screen across two layers. A one-line
  edge, accepted on purpose.

That is why `arca.registry` is imported by path rather than re-exported from
`arca`: importing it pulls the ORM in, and merely importing the adapter should
not require Django's app registry.

## Domain modules

`service/domain/<name>/` has a fixed shape:

- `schemas.py` - dataclasses: inputs and read models.
- `calc.py` - pure arithmetic, no ORM and no I/O.
- `use_cases.py` - module-level functions; the steps that need a port.
- `serializers.py` - DRF serializers for the domain's own shapes.
- `viewsets.py` - ViewSet classes; `@action`s make one call into `use_cases`.

`models.py` never appears under `service/` - ORM models live only in `data/models/`. Neither does a `Manager`: that word belongs to Django, and the writes belong to the models (see **Where logic lives**).

The domains themselves:

- `access` - who can reach whose books, and how they got there. `use_cases.register_taxpayer` claims a CUIT and makes the caller its owner, in one transaction; `gaps` says what a taxpayer still needs and what each absence blocks, read off the model every time so gaining a certificate closes the line without anything being told; `last_reads` says when each feeder (IPC, market, experiment, movements) last wrote, for the home's "Al día". Registration is the one flow whose authorization is **not** `data/visibility.py`'s: at registration there are no books to have a role on, so what guards it is `Taxpayer.objects.register` refusing a CUIT somebody already holds. Not called `auth`: authentication is `service/gateway.py` and allauth, authorization is the visibility table, so a domain by that name would hold neither.
- `billing` - the Factura E lifecycle. `use_cases.monthly` runs one month end to end (draft → authorize → link the payment); `catch_up` and `crosswalk` do it for a whole window and report it read-only; `close_period` reads one month's state; `cancel`/`credit` issue notas de crédito; `valuation` reconciles the reversal journal. The primitives they build on are `draft_monthly`, `authorize`, `record_portal_authorization` and `portal_sheet`.
- `payments` - `use_cases.import_payoneer` labels the table's Payoneer rows with what each does to the balance, so the credits among them read as `Payment`s; `classify.py` is the pure rule and `matching.py` only proposes which credit settles which invoice, it never links.
- `extractos` - `use_cases.load_report` parses one institution's report into `Movement`, idempotently; `reconcile`, `reconcile_settlements` and `unsettled_withdrawals` report where the table and the ledger disagree. See `docs/extractos.md`.
- `expenses` - `use_cases.categorize_all` writes each ARS outflow's `categoria` from the rules table plus the human's overrides; `category_totals` reports it, grouped by category, month or institution; `baseline` reduces it to a per-category monthly run rate; and `project` walks that forward against `Goal` and `Obligation` to say where the next twelve months go tight; `outlook` is the home's glance - pesos in and out per month and spending per week, the last complete ones; `rate_in_force` is the USD quote the pages convert at, read off `ExchangeRate` since 2026-10-04 - until then `interface/web/books.py` carried `RATE = Decimal(1513)`, one September day's quote printed as every page's fact. `projection.py` is the pure core. This domain owns more than one question deliberately - see the 2026-09-17 projection spec, in git history.
- `movements` - the passes over the one table money moved lands in, in dependency order; `PASSES` is the order and `run_pipeline` walks it. A composition of `payments`, `expenses` and `extractos`, not a new model.
- `planning` - the goals' plan: `use_cases` schedules when each planned goal can be paid, in the order given, and what the alternatives cost (`plan_goal`, `planned_terms`, `readiness`, `order_goals`, `revise_goal`, `borrow_or_save`); the `Goal` API's serializers and viewsets live here. See `docs/PLANNING.md`.
- `balances` - the stock side. A balance is asserted once and run forward: `use_cases.derive` takes each account's bottom line off the statement rows that carry one, `use_cases.record` takes by hand the ones no institution prints, and `use_cases.position` runs each close forward over the movements since it, totals the result into net worth, splits the assets by currency and measures them against the expenditure baseline as a runway in months. `Cutoff` is the policy half - one taxpayer's books closed through a date, before which a reading cannot be rewritten. `calc.py` is the pure core. The one domain whose input is partly a person reading a statement, because two of the four institutions report no running balance. See `docs/BUDGET.md`, "Where the stock comes from".
- `reporting` - `use_cases.archive` writes one spreadsheet a year to the shared Drive folder, the month as a tab. Reads only. See `docs/ARCHIVE.md`.
- `setup` - `use_cases.import_bundle`, `export_bundle`, `status` and `starter` configure a taxpayer's books from one document: the category vocabulary and its roles, the rules that read statements, the payees named by hand, who sends bills, and the declared parameters. The repository ships only a neutral starter; a person's own setup is rows. See `docs/SETUP_DATA.md`.
- `regularization` - `use_cases.recategorization_penalty` prices the omission: the cuota gap over the window, the resarcitorio on it, and the art. 26 multa bracket. `unrecognized_months` and `backlog_scaffolding` say which months were never recognized and what issuing them would cost. It also scored and projected the contadores' proposed strategies until 2026-09-17; that went with the decision it served - see below.
- `tax` - `use_cases.position` (HTTP) and `.taxpayer_status` (CLI) answer the rolling 12-month ARS, implied category and headroom - derived, never stored.
- `inflation` - `use_cases.fetch` loads INDEC's IPC into `PriceIndex` and `fetch_labor` the wage and canasta series into `LaborIndex`, both idempotently; `cross_reference` reads each group's spending against its IPC division and the wage against prices and the canasta; `real_wage` reads the wage against prices and the canasta (no page draws it yet). See `docs/INFLATION.md`.
- `market` - `use_cases.fetch` loads BCRA's reference rates into `MarketIndex`; `report` reads them as TNA/TEA/TEM. The `bcra` adapter is its writer.
- `savings` - `use_cases.terms`, `project_plans` and `strategies` resolve an investment kind and project plans and placement strategies; `resolvers.py` is the per-kind table and `calc.py` the pure core. See `docs/SAVINGS.md`.

`billing`, `planning` and `tax` are the only three with a `serializers.py` and a `viewsets.py`; the other ten are reached from the CLI, and `access` from the web shell as well. A domain grows the HTTP pair when something asks for it over HTTP, not on principle - `payments` has its rows on the API through `service/payment.py` and no viewset of its own.

The standing answer to event-driven architecture is *declared order, not a
dispatcher*: there is deliberately no event bus, no Django signals and no event
outbox (the `tasks` database is a job queue for the cadence, not an outbox for
domain facts). A step the caller needs done — `record_reversal`,
`Membership.grant`, `link_payment` — stays an explicit call, never a subscriber, so
a reaction cannot be lost to a handler nobody wired. `ReversalEntry` remains the one
append-only journal, kept for the one fact a later write would destroy (what a
credit note netted at the rate in force that day). `Movement.category` and
`AccountBalance` are deliberately overwritten rather than journalled: the source
statements rebuild the movement, and `source=LEDGER` vs `MANUAL` already separates a
derivation from a correction, so a second journal would record what the reports
already recompute.

`movements.PASSES` is the pipeline's order, data rather than call order, and a
convention test pins it; each pass stays idempotent (it writes only the rows whose
column changed), so the chain is safe to walk twice. It is a tuple walked
synchronously — declared data, not a bus and not a subscriber registry.

## Invariants enforced in code

1. **`Invoice.amount_ars` is frozen.** Computed once from the rate for the business day before emission, by `freeze_valuation()`, which no-ops when the invoice is already valued - so no code path can revalue an issued comprobante at a later rate. That, rather than a check in `save()`, is what makes it immutable; see "No validation in `save()`" above. `tests/scaffolding/data/models/test_invoice.py` and `tests/scaffolding/service/billing/test_use_cases.py`.
2. **`Invoice.arca_cmp_id` is unique per taxpayer.** WSFEX idempotency key; a retry cannot create a second row. Per taxpayer and not globally, because ARCA scopes the key to a CUIT - two taxpayers legitimately hold the same one. `uniq_comprobante` is the same story: puntos de venta are assigned per CUIT and numeración restarts at 1 within each, so two taxpayers' first Factura E are both `(4, 19, 1)`.
3. **`Payment` and `Expense` are readings of `Movement`, not tables.** Proxy
   models over the one movements table - the inflow reading and the outflow one.
   `Payment.gross`/`.fee`/`.net` are properties over `inflow` and the matched
   invoice, so `match()` writes only the link and the figure the rail reported is
   never overwritten. Membership is `Movement.kind`, not the sign: a Payoneer
   balance conversion is an inflow that is not income.
4. **`Payment` and `Settlement` are separate.** Different dates and currencies; Settlement is the BCRA-relevant event (funds credited to a local account), and it hangs off the account, not off a payment or an invoice. `effective_rate` is credited-per-sent on the row itself; comparing it to the invoice's ARCA rate is a report, not a foreign key.
5. **Unmatched payments are visible.** `Payment.invoice` is nullable; `GET /payments/unmatched/`.
6. **Valuation freezes at draft time**, because the rate is a function of `fecha_emision`. If emission moves: delete, redraft. Stricter than necessary, deliberately.
7. **An authorized invoice cannot be un-issued.** `void()` refuses it and `reject()` refuses it: ARCA holds the CAE, and a status flip would drop the income out of `tax.position()` and make `close_period` report the month as undrafted. Reversing a real Factura E means a Nota de Crédito E (`CbteTipo.NOTA_CREDITO_E`), which this tool does not issue yet. For the same reason `billing.use_cases.authorize` refuses anything but a DRAFT before it opens a connection - otherwise ARCA spends a número on a comprobante the ledger will not record.

    Neither can it be deleted, since 2026-09-20: `DELETE /scaffolding/{id}/` answered 204 on an authorized comprobante and the admin offered the button, so the same income left the totals by a shorter route. `Invoice.delete()` refuses once AUTHORIZED (a draft stays deletable - delete and redraft is the documented fix when emission moves), `InvoiceAdmin.has_delete_permission` closes the bulk action `QuerySet.delete()` would take around it, and the inline locks an authorized comprobante's lines. `status` is never an admin form field at all - a transition is a named mutator, not an assignment.
8. **Every authorized credit note is journalled.** `Invoice.authorize()` writes a `ReversalEntry` when `reverses` is set - in the mutator rather than the shell so no path can authorize one without recording what the pair netted, and in the same transaction as the save so neither can happen without the other. The write comes after the save because the net it records counts the note itself. It is an event record, not a cache: the ledger holds current state, the entry holds what was true when the note was authorized. `scaffolding valuation` reconciles the two and reports a pair it never recorded, a pair whose figures moved, or an entry whose comprobantes are gone.

    It was a JSONL file under `var/` until 2026-09-10, and two arguments moved it. A file cannot commit with the row it accompanies: wrapping the pair in `transaction.atomic()` stopped a refused entry leaving an AUTHORIZED row behind, but a rollback *after* the line was written still left an entry for a comprobante the ledger no longer had. And the reason given for keeping it outside the database - that a separate file resists tampering - does not survive inspection, because 0600 on a file owned by the user who runs the tool is one `$EDITOR` away. What was given up is independence from a database restore; what was gained is a real transaction, a join instead of reading the file whole, and one place in this project touching the disk instead of two. `ReversalEntryAdmin` refuses add, change and delete, so the one interactive path cannot make the two sides agree by editing the wrong one.

    Typed columns for what the reconciliation matches and compares on - the labels, the dates, the nets - and a `recorded` JSON field holding both sides verbatim, so a field added to a comprobante needs no migration here. The snapshot quantizes to the columns' own precision: `str(Decimal)` renders whatever the in-memory value carries, which made the same authorization record `1480` or `1480.000000` depending on where the object came from.
9. **A drafted credit note already claims what it would reverse.** `get_uncredited_amount()` counts only authorized notes, because only a CAE makes a reversal real - but the reversal factories measure against `get_uncommitted_amount()`, which counts drafts too. Otherwise `cancel()` twice drafted two notes for the whole amount, each legal on its own, and authorizing both left the factura standing at minus its own value.
10. **A reversal nets to zero in dollars and to the rate movement in pesos.** Each comprobante is valued once at the rate for its own `fecha_emision`, so cancelling a USD 6,000 factura frozen at 1480 at a later 1500 leaves −120,000 ARS. That figure is real - the rolling twelve-month monotributo total moves by it - and is printed by `scaffolding creditnote` and `scaffolding valuation` rather than rounded away. `cancel()` cannot reuse the original's rate without sending ARCA a rate it did not register.

## ARCA adapter boundary

`interface/adapter/arca/ports.py` defines three Protocols. The service layer imports only these.

```
arca/
  ports.py       the three Protocols and their payload dataclasses
  endpoints.py   ARCA_ENV → urls + certificate filename
  soap.py        envelope · POST · TLS · fault          I/O
  calendar.py    business-day arithmetic, and ART - the timezone the WSAA login
                 ticket is stamped in. It lived in ticket.py until 2026-09-10.
                 WSFEX dates do not use it: a Fecha_cbte is a calendar day, not an
                 instant, and `.replace(tzinfo=ART)` on one only looked like a
                 conversion (see wsfex/mapping.parse_arca_date).
  wsaa/
    mapping.py   TRA built, CMS signed, answer parsed   PURE - the functional core
    client.py    login, and the credentials cache       I/O
    ticket.py    the ticket's 0600 cache on disk        I/O
  wsfex/
    mapping.py   build requests, parse responses        PURE - the functional core
    client.py    the four operations, in domain types; implements the rate and
                 the authorizer port
  padron/
    mapping.py   build and parse the constancia query   PURE - the functional core
    client.py    the padrón lookup, in domain types     I/O
  manual.py · dry_run.py · registry.py
```

Only `soap.py`, `wsaa/client.py` and `wsaa/ticket.py` touch the network or the disk. `mapping.py` is where every wire-format decision lives, which is why it can be tested against envelopes recorded from ARCA rather than against a mock.

### What the package exports

`arca/__init__.py` is the surface: the three clients, the endpoint table, the calendar, the reference-table names, and `soap` as a module. Everything else is reached by path, and each exclusion means something:

- `arca.ports` - a dependency on the Protocol boundary should read as one; `service/` depends on this, never on `arca`. That includes `ReversedComprobante`, which `billing.schemas.PortalSheet` carries: the sheet had a twin of it until 2026-09-10, and two dataclasses with the same four fields differed only in the module they sat in.
- `arca.registry` - same, plus it reaches the ORM through `manual` (see above).
- `arca.dry_run` and `arca.manual` - they exist to be *selected*; naming one outside the package bypasses the setting that chooses it.

The three services are one package with the same three parts - `mapping` (pure), `client` (the shell), `__init__` (the surface) - and each keeps whatever else it needs inside, which is why the WSAA ticket cache is `wsaa/ticket.py`. Each has a `build_client()` from settings, and `wsfex`'s and `padron`'s build on `wsaa`'s rather than repeating the certificate convention; they are reached as `wsaa.build_client()`, `wsfex.build_client()` and `padron.build_client()`, since flattening them would collide.

`WsfexClient` *is* exported, because `bin/` builds one directly to probe ARCA.

The convention, in one line: **classes and functions by name, transport and wire-format modules by module** - `soap.post`, `mapping.authorize_body`. Inside the package siblings import each other directly (`from . import soap`), never through `__init__`, which would be circular.

The ports and who implements them:

- `RateProvider` - `manual`, no network, selected by `ARCA_RATE_PROVIDER=manual`; or `wsfex`, over the network, selected by `ARCA_RATE_PROVIDER=wsfex`.
- `InvoiceAuthorizer` - `dry_run`, no network, selected by `ARCA_AUTHORIZER=dry_run`; `manual`, no network, selected by `ARCA_AUTHORIZER=manual`; or `wsfex`, over the network, selected by `ARCA_AUTHORIZER=wsfex`.
- `TaxpayerRegistry` - `padron`, over the network: the padrón and constancia lookups against ARCA's registration service.

`wsfex` implements the rate and authorizer ports with one client. `manual` is the portal bridge: `authorize()` always raises - the CAE from Comprobantes en línea is recorded via `billing.use_cases.record_portal_authorization`, which goes through the same `Invoice.authorize()` mutator and so enforces the same invariants. `dry_run` exists for tests and mints fake CAEs; never run it against real data.

`FEXGetCMP` - ARCA's "read back a comprobante" operation - is deliberately not
implemented. The failure it would recover from is a CAE lost to a dropped
connection, and `Reproceso` already covers that: the invoice keeps its
`arca_cmp_id`, so a retry returns the original CAE rather than issuing a second.
Recovering by query would be a second mechanism for a case the first one handles.

`wsfex` authorizes a Nota de Crédito E as well as a Factura E, confirmed in
homologación on 2026-09-10 (CAE 76377016798627, cbte_tipo 21). Two wire details
carry it, both read from ARCA rather than guessed: `Cmps_asoc` names the
comprobante being credited, at position 20 of `ClsFEXRequest`; and `Fecha_pago` is
**omitted**, which ARCA insists on for a credit or debit note - error 1673, "para
las notas de debito y credito no informar fecha de pago".

The rate is **asked for**, not computed: ARCA validates `MonCotiz` against its own registered value for the prior business day (WSFEv1 validation 10038; WSFEX analogue is `GetParamMonConCotizacion`). `calendar.previous_business_day` only chooses the date to ask about.

## Sensitivity classification

### Never in the repo, never in the DB

- ARCA certificate + private key - in `etc/secrets/` (gitignored), mode 0600. Issues fiscal documents in your name.
- WSAA token/sign - in `var/wsaa-{env}-{service}.json`, 0600, gitignored. Bearer credential, ~12h. On disk rather than in memory because WSAA refuses a second login while one is valid, so in-memory caching means a refused login after every restart.
- `SECRET_KEY` - in `.env`. Session forgery.
- CUIT - in `.env`. Ties every record to you.
- Signed contract PDF - on disk; `Contract.document_path` only. Confidential, clause 14(b).

### In the DB - the SQLite file is itself sensitive; keep it on an encrypted volume

- Contract fee and terms, on `Contract`. Exportable to contador: yes - 14(b) permits tax advisors.
- Scaffolding (CAE, nº, dates, amounts), on `Invoice`. **Yes - exactly what they need.**
- Payments and settlements, on `Payment` and `Settlement`. Yes.
- Bank identifiers - `Account.cbu`, `.alias`, `.account_number`, `.routing_number`, `.swift`. **No.** Excluded from `AccountSerializer`; tested.
- Account balances, on `AccountBalance`, and the date they are closed through, on
  `Cutoff`. Yes - a contador reconciling a period asks for both. The bank
  identifiers they hang off do not travel with them: `AccountBalance` carries the
  account and the figure, never the CBU.
- Bank movements and the spending read off them, on `Movement` / `Expense`. Yes.
  There was a `PERSONAL` / `PROFESSIONAL` split on `Expense` until 2026-09-17,
  meant to decide what could be exported. It went with the table: everyone who can
  open this database can open all of it, so the distinction cost a column and
  bought nothing.
- Registered category, on `MonotributoStatus`. Yes.

### Public reference data

`MonotributoScale`, `ExchangeRate` (ARCA-sourced), `AutonomosContribution`,
`CompensatoryRate`, `LegalThreshold`, `Client.arca_country_cuit`. The dated
parameters carry a `valid_from`, are seeded idempotently from
`data/reference/*.json` via `loadreference`, and are resolved at the shell with
`in_force(as_of)` - never read as a module constant, because a figure that moved
silently is the one way a projection understates a cost.

### Interchangeable third parties

- ARCA transport - currently hand-rolled SOAP over `urllib` + `cryptography`; the swap costs `interface/adapter/arca/soap.py`.
- Rate source - currently ARCA (WSFEX); the swap costs one adapter file.
- Payment rail - Payoneer (CSV import) and a direct bank transfer (recorded by hand); matching is rail-agnostic. The swap costs an `Institution` value + a parser. There was a separate `Rail` vocabulary until 2026-09-17; it was deleted because a settlement's leg is looked up in the movements table by `source`, and `Rail.WIRE` matched no institution, so a wire's leg could never be found.
- Bank - Galicia, Nación, Payoneer and Amex; the swap costs an `Account` row.

## Deliberate divergences

SQLite via `env.db()`. No structlog, CORS, Postgres. Out of scope: IVA/Ganancias - if the monotributo ceiling is crossed, `tax` grows a second domain; nothing else changes. Deployment was listed here as out of scope until 2026-10-11; it is `docs/INFRASTRUCTURE.md`'s - the wheel, one process, no docker. Docker is there only as the throwaway sandbox.

This paragraph put multi-user and JWT out of scope until 2026-09-18, and said session auth because there was one local user. All three were true and are not: the tool now has identity, more than one taxpayer, and one way to authenticate an API request: the session. It stays because the admin is this tool's primary UI and the browsable API depends on it.

The JWT cookie went on 2026-09-18, with `dj-rest-auth` and `simplejwt`. It was
obtainable only through `/api/v1.0/auth/login/`, which takes a password - and
`SOCIALACCOUNT_ONLY` removes the local signup while allauth calls
`set_unusable_password()` on every social one
(`allauth/socialaccount/adapter.py:156`), so the only account that could ever
use it was a `createsuperuser` one, which already had the session. The password
reset endpoints beside it were mounted with no email backend configured. Two
dependencies, two settings blocks and six routes, so the operator could log in
twice.

`service/authentication.py` is what is left: DRF's `SessionAuthentication` plus
the `WWW-Authenticate` header it omits, because without one DRF answers 403
where it means 401. It keeps a module of its own for a layering reason - DRF
reads `DEFAULT_AUTHENTICATION_CLASSES` from inside `rest_framework/views.py`, so
anything named there is imported mid-initialisation and cannot import `APIView`,
which `tenancy` does.

There was a third until 2026-09-18: `data.AccessToken`, a hashed personal access
token behind `Authorization: Token <secret>`, which `scaffolding login --no-browser`
pasted back. It went because nothing could mint one. `AccessToken.objects.issue`
had no caller outside the suite - `AccessTokenAdmin` refused add, and a Google
signup could not reach that page anyway - so the flag asked the operator for a
secret no shell in this project could produce, and the DRF authenticator guarded
a door with no key. 172 lines of `src` and 183 of tests, none of it reachable.
`migrations/0002` drops the table rather than `0001` being edited, because the
rows are credential digests and an edited initial migration leaves them behind.

The `AccessTokenScheme` drf-spectacular extension went with it; the schema now
documents the two ways that work. What would bring it back is a non-browser
client, and the missing half was always the mint, not the check.

## Identity, ownership and visibility

Three concepts, and conflating any two of them is what forces a painful migration later.

- **`BaseUser`** is the login *and* the person: an email, the flags Django needs, the name Google returned, and `active_taxpayer` - "which books am I looking at", a preference that every shell has to resolve.

  It was two tables until 2026-09-18, with the person in a 1:1 `Profile`. The argument for the split was that swapping an auth model is the expensive operation this design is arranged to avoid doing twice, so the auth table should have few reasons to change - but that swap already happened in `0001`, where `AUTH_USER_MODEL` became `data.BaseUser`, and Django's own `AbstractUser` carries a name for the same reason this one now does. What the split cost was a join on every admin and API request, a `Profile.objects.of(cast(BaseUser, request.user))` at ten call sites, and an "every account has a profile" invariant needing a factory, a reader that raises, enforcement on two creation paths and a convention test - one of which, `access.register_taxpayer`, was quietly calling the factory and so inventing a person for whoever registered books. `migrations/0004` carries the columns and repoints `Membership`, and is reversible because it runs against a ledger.
- **`Taxpayer`** is identity *in ARCA*: the CUIT, the certificate proving it, the punto de venta, the Drive folder the archive writes to. A remote account, the same shape as allauth's `SocialAccount`, which is identity *in Google*. Both answer "who am I to an external system, and what proves it", which is why the ARCA certificate lives on one and the Google refresh token on the other, and neither on `BaseUser`.
- **`Membership`** joins an account to a taxpayer with a role. Being a contador is not intrinsic to a person - it is a relationship to someone else's books, and the same person can be a monotributista and their sister's contador - so there is a role on an edge and no `AccountantProfile`. Removing the last `OWNER` is refused: books nobody can administer are books nobody can rescue.

**Every table that is not reference data carries `taxpayer`.** No exceptions and no second taxonomy for tables whose parent already implies one - that split saves a few columns and costs a join in half the scoping queries plus the question "which kind is this?" at every call site. The duplication cannot drift, because a child's taxpayer is never an argument: `Invoice.objects.draft()` sets each line's from the invoice it is building, and a parent from different books is refused by `same_taxpayer` in the factory, which is the only home a rule no constraint can span two tables has.

Reference tables stay unowned - the monotributo scale, the thresholds, the rates, the category taxonomy are public facts, and a per-taxpayer copy of the scale would be a per-taxpayer copy of the law.

**Ownership says whose a row is; visibility says what a role may do with it.** Both are asked, in that order. The first is `get_queryset` - in `OwnedAdmin` for the admin and `ScaffoldingModelViewSet` for HTTP - and `get_object` resolves through it in both, so another taxpayer's row is a 404 on a guessed id before any permission is asked.

**What a write points at is scoped the same way, since 2026-09-20.** Narrowing the row was not narrowing its relations: a PATCH could repoint an owned contract at another taxpayer's client, and the admin's dropdown offered that client as a choice. `serializers.base.OwnedSerializer` narrows every related field on an owned model to the request's books - validation and the browsable API's choices are the same queryset, and without a request the choices are empty, never everybody's - and `admin.base.narrow_choices` is the same answer for the change form. The taxpayer column itself is never on the wire (`base.HIDDEN`, now enforced across the custom serializers too, which is how a PATCH could move a settlement between books).

**A page is not gated by its link.** The graduated books walk Movement, Goal and Obligation, which the visibility table grants separately - an accountant reads every movement and no goal - so `interface/web/books.BookPage` asks Django's own permission question, answered by `RoleBackend` off the same table as the admin and the API. Until 2026-09-20 the pages checked only login, and a VIEWER could POST a goal `data/visibility.py` grants only the owner.

The second is `data/visibility.py`, read by `data/backends.RoleBackend` and nothing else. It answers Django's own two questions - `has_perm` and `has_module_perms` - off the role the person holds on the books they are looking at, so every default asker works unchanged: `ModelAdmin.has_*_permission`, `{% if perms.data.add_invoice %}`, and DRF's `DjangoModelPermissions`. Two shells, one asker.

**No object.** The role is one value per request, and which rows is already settled by the paragraph above, so a per-object check would be a second answer to a settled question. That is also why the `X-Taxpayer` header went: it made "which books" a per-request fact, and a backend cannot see a header.

There was a `TaxpayerBackend` that answered only the object question and declined the global one, deleted on 2026-09-18 in `4287167` because the admin index rendered empty for every member. The reason given - that a backend must decline the global question to leave superusers to `ModelBackend` - is wrong: `PermissionsMixin.has_perm` and `.has_module_perms` both return True for a superuser *before* consulting any backend. What emptied the index is that `has_module_perms` was never implemented, and `_user_has_module_perms` is an `any()` over the backends, so `ModelBackend` answered alone and a Google signup has no `Permission` rows. Implementing the method was the whole fix, and it took `VisibleAdmin` and `ResourcePermission`'s hand-rolled half with it.

The table is minimal by default: a resource absent from a role's row is invisible to it, and a model nobody classified belongs to nobody - `test_conventions.py` fails until someone writes down whose it is. The clearest case for it existing is that an accountant cannot see `Goal` or `Obligation` at all: what someone is saving for is not part of the job, and ownership alone could not express that, because the contador is a legitimate member of exactly those books.

**A Google signup is `is_staff`.** The admin is this tool's UI, so a login that cannot reach it authenticates people and puts them nowhere. That is safe because every changelist is already narrowed by membership and every object permission already goes through `has_perm`: the flag opens the door, `data/visibility.py` furnishes the room. `is_superuser` is never granted by signup - a superuser bypasses the backend entirely, which is what makes that distinction load-bearing.

**There is no second row for a signup to create.** That paragraph used to explain how "every account has a profile" was kept true on both creation paths - the gateway and `createsuperuser`. Folding the person onto the login deleted the invariant rather than enforcing it better, which is the cheaper of the two.

**Scoping is explicit at each shell, never in a default manager.** A manager that filtered by "the current taxpayer" would need the request, and that means thread-local state - invisible in the query it shapes, wrong in a management command, and impossible to test both ways. `service/tenancy.py` answers *which books* for HTTP, `data/admin/base.person()` for the admin, and `ScaffoldingCommand.taxpayer()` / `.acting_user()` for argv. The web shell adds no fourth mechanism: the profile page's subject is the person, so it reads `active_taxpayer` and `taxpayers()` straight off `request.user`, which is the same lookup `OwnedAdmin.active` makes.

**A superuser is not offered an Add form in the admin when it has no active books.** Adding is the only action that needs to know which books to file the row under; view, change and delete work on rows that already name their own. `has_add_permission` asks that before it asks `allows`, because a superuser short-circuits every permission and would otherwise be handed a form `save_model` can only save as null.
